# 问题理解

## 任务链

比赛总时长 20 分钟，系统需要形成感知、决策、执行闭环。

### 阶段一：仓储通道

- 上 4 阶楼梯。
- 通过 15 度下坡。
- 通过含乱石和 2 条减速带的不平路面。
- 机器人摔倒或程序崩溃时保留已完成地形得分，并进入后续任务。

### 阶段二：零件分拣

- 系统随机发布 A、B 或 C 零件任务。
- 工作台上 A/B/C 各 3 个，位置随机、尺寸相同。
- 识别目标类别，将 3 个正确零件逐个放入收纳箱。
- 必须避免误抓错误类别，因为每个错误零件扣分。

### 阶段三：搬箱入库

- A 对应红色货架，B 对应黄色货架，C 对应蓝色货架。
- 搬起收纳箱，使其投影离开分拣桌。
- 将箱子放到对应货架中层。
- 放置后 10 秒内箱子不得掉落。

## 工程约束

- 官方平台封装在 Docker 中，推荐 Ubuntu 20.04 与 NVIDIA GPU。
- 只能通过指定接口读取 observation、任务参数和机器人参数，并输出规定 action。
- 最终实现入口为 `TaskSolver(task_params, agent_params)` 和 `next_action(obs)`。
- 官方明确禁止修改 `submission/task_launcher.py` 等核心文件。
- 需要提交源代码、完整任务脚本、说明文档、测试报告和 Docker 部署说明。

## 风险优先级

1. 接口合规和可运行性。
2. 稳定通过阶段一的分段得分。
3. 可靠识别并抓取至少 1 个正确零件。
4. 完成 3 个正确零件分拣，避免错误零件。
5. 先实现搬起箱子，再优化正确货架与稳定放置。
6. 最后优化总用时、泛化和创新性。

## 待仿真确认

- 官方 launcher 只接受 `TaskOne` 和 `TaskTwo`，但 observation 说明中出现 `TaskThree`。需要在真实环境确认阶段二与阶段三是否合并在 `TaskTwo`。
- `task_goal` 的实际字段结构、颜色/类别编码和随机化范围。
- 相机帧率、深度单位、坐标系和 object pick 判定阈值。
- 任务失败后如何继续下一阶段，以及 `score.yaml` 的准确续跑行为。
